# ADR-0046: Automatic Git Repository Initialization for Workspace Management

## Status

Accepted

## Context

KodeHold's workspace management relies on git repositories in several places, but neither `ws_init()` nor `ws_adopt()` guarantees that a workspace has a `.git` directory.

### Current Behavior

**`ws_init()` (line 36 of `scripts/workspace.sh`):**
Creates the workspace directory tree (`docs/design`, `docs/adr`, `src`, `tests`), writes a design doc template, ADR index, `.kodehold-state`, and `.gitignore` — but never runs `git init`. After `ws_init()` completes, the workspace has no git history, no tracked files, and no working branch.

**`ws_adopt()` (line 108 of `scripts/workspace.sh`):**
Creates a symlink to an existing project, then checks for `.git` only to count commits for the design doc:

```bash
if [ -d "$ws_dir/.git" ]; then
  commit_count=$(git -C "$ws_dir" log --oneline 2>/dev/null | wc -l)
fi
```

If the adopted project has no `.git`, the commit count is zero, and no git repository is created. The script moves on without warning.

### Scope of the Problem

An audit of all 6 workspaces reveals **2 of 6 lack `.git`**:

| Workspace | Has .git | Notes |
|-----------|----------|-------|
| agentmemory | ✅ | Created via `init` |
| bob | ✅ | Created via `init` |
| deepresearch | ❌ | Missing |
| media-health-dashboard | ✅ | Created via `init` |
| pai-model-router | ❌ | Missing |
| radarr-lang-router | ✅ | Created via `init` |

Both non-git workspaces were created early in KodeHold's development, before the workspace manager reached its current form.

### Downstream Failures

The absence of `.git` causes silent or noisy failures in at least three subsystems:

1. **Commit protection protocol (`scripts/gate.sh`, line 250).** The REVIEW gate checks commit messages for review keywords via `git log --oneline -20`. Without a `.git` directory, `git log` returns an error and the check silently passes with no review evidence.

2. **Slug resolution priority 2 (`ADR-0036`).** The project slug specification defines `basename(git rev-parse --show-toplevel)` as the second-highest priority resolution source. Without `.git`, this falls through to `basename(cwd)` — which may produce a different slug than if the workspace had its own git repo. This creates an inconsistency between the workspace's catalog entry (slug) and the slug the agentmemory hooks would resolve.

3. **Working tree cleanliness check (`scripts/gate.sh`, line 312).** The REVIEW gate checks `git diff --quiet` to verify no uncommitted changes. Without `.git`, this check produces a non-zero exit code with a "not a git repository" error, incorrectly blocking the transition.

4. **Workspace isolation.** Workspaces without their own `.git` are subject to the parent KodeHold repo's git state. A `git diff` in the workspace directory may report changes from entirely unrelated files in the parent repo.

### Design Constraints

- Must not disrupt existing non-git workspaces — backfilling is opt-in
- Must not block workspace creation when git is unavailable (CI containers, minimal environments)
- Must respect ADR-0012's guiding principle: "Existing projects already have code, tests, git history, and build systems — KodeHold must not disrupt these." Creating git in a non-git project is *enabling*, not disrupting
- Must produce clean initial commits that are identifiable as auto-generated by KodeHold

## Decision

We introduce automatic `git init` in both `ws_init()` and `ws_adopt()`, with graceful degradation when git is not available. We also add a standalone `ensure-git` subcommand for backfilling existing non-git workspaces.

> **Existing .git protection:** If a `.git` directory already exists (e.g., an adopted project already has its own git history), both `ws_init()` and `ws_adopt()` gracefully skip git initialization. The `[ ! -d "$ws_dir/.git" ]` guard clause prevents re-initialization — this protects existing git repos from accidental data loss or double-initialization.

### 1. `ws_init()` — After `.gitignore`, Before Catalog Registration

Insert after the `.gitignore` block (line 95) and before the catalog registration (line 97):

```bash
# Initialize git repository for workspace isolation and lifecycle checks
if command -v git &>/dev/null; then
  if git init "$ws_dir" >/dev/null 2>&1; then
    git -C "$ws_dir" add -A >/dev/null 2>&1
    git -C "$ws_dir" commit -m "Initial commit" >/dev/null 2>&1
    pass "Git repository initialized at $ws_dir"
  else
    warn "git init failed — workspace will not have version control"
  fi
else
  warn "git not found — workspace will not have version control"
fi
```

**Timing matters:** Git init happens after `.gitignore` is written but before catalog registration. This means the `.gitignore` patterns take effect immediately for the initial commit, and the catalog entry is created after git state is established (future-proofing against any catalog checks that might depend on git presence).

### 2. `ws_adopt()` — After Commit Count Check, Before Design Doc Creation

Insert after the commit count block (line 182) and before the design doc template (line 184):

```bash
# Ensure git repository exists for lifecycle checks
if [ ! -d "$ws_dir/.git" ]; then
  if command -v git &>/dev/null; then
    git init "$ws_dir" >/dev/null 2>&1
    git -C "$ws_dir" add -A >/dev/null 2>&1
    # Use identifiable message to distinguish KodeHold-created commits
    git -C "$ws_dir" commit -m "Initial commit — adopted by KodeHold" >/dev/null 2>&1
    pass "Git repository initialized at $ws_dir"
  else
    warn "git not found — adopted project will not have version control"
  fi
fi
```

**Key design choice:** The initial commit captures the project state *after* `.kodehold-state` is written (it is created at line 139 of `workspace.sh`, before the proposed git init at line 183) but *before* `docs/design/` and `docs/adr/` templates are created. This means `.kodehold-state` is part of the initial commit alongside original project files, while documentation artifacts remain **untracked**:

```
# After ws_adopt():
#  ── Initial commit ──
#  Original project files (all existing code, tests, configs)
#  .kodehold-state              # Created at line 139, before git init
#
#  ── Untracked ──
#  docs/design/README.md  # KodeHold documentation
#  docs/adr/README.md     # KodeHold documentation
#
#  ── .gitignore ──
#  (KodeHold artifacts intentionally not added — they are
#   project-specific management data, not part of the project source)
```

### 3. New Subcommand: `ensure-git`

For backfilling existing workspaces that lack `.git`:

```
Usage: bash scripts/workspace.sh ensure-git [<name>]
```

| Argument | Behavior |
|----------|----------|
| *(none)* | Scan all cataloged workspaces, report which have/ lack `.git` |
| `<name>` | Initialize git in the named workspace if missing |

**Dry-run mode:** Always supported via an internal check — scan reports without modifying:

```
$ bash scripts/workspace.sh ensure-git
Scanning 6 workspaces...
  ✅ agentmemory — has .git
  ✅ bob — has .git
  ❌ deepresearch — NO .git (would initialize)
  ✅ media-health-dashboard — has .git
  ❌ pai-model-router — NO .git (would initialize)
  ✅ radarr-lang-router — has .git

2 workspaces missing git. Run: bash scripts/workspace.sh ensure-git <name>
```

**Apply mode:**

```bash
ws_ensure_git() {
  local name="$1"
  local ws_dir="$WORKSPACE_ROOT/$name"

  if [ ! -d "$ws_dir" ]; then
    fail "Workspace '$name' not found"
  fi

  if [ -d "$ws_dir/.git" ]; then
    pass "'$name' already has a git repository"
    return 0
  fi

  if ! command -v git &>/dev/null; then
    warn "git not available — cannot initialize '$name'"
    return 1
  fi

  if git init "$ws_dir" >/dev/null 2>&1; then
    git -C "$ws_dir" add -A >/dev/null 2>&1
    git -C "$ws_dir" commit -m "Initial commit — backfilled by KodeHold" >/dev/null 2>&1
    pass "Git repository initialized for '$name'"
  else
    warn "git init failed for '$name'"
    return 1
  fi
}
```

> **Dispatch entry required:** Add the following case to the command dispatch block (around line 427 of `scripts/workspace.sh`, before the `*)` catch-all):
> 
> ```bash
> ensure-git)
>   [ -n "${2:-}" ] || usage
>   ws_ensure_git "$2"
>   ;;
> ```

### Graceful Degradation

Every git operation is guarded:

| Condition | Behavior |
|-----------|----------|
| `git` not installed | `warn` → continue without aborting |
| `git init` fails (permission denied, read-only FS) | `warn` → continue without aborting |
| `git add -A` adds nothing (empty directory) | `git commit` fails → `warn` → continue |
| Already has `.git` | Guard `[ ! -d "$ws_dir/.git" ]` skips init |

The keyword: **warn, never fail**. Workspace creation must never be blocked by git unavailability.

### Alternatives Considered

**1. Opt-in flag on existing commands (e.g., `ws_init --git`, `ws_adopt --git`).**
Rejected: Requires users to remember an extra flag, increasing cognitive load. Git init is a universally beneficial safety net (error messages improve, slug resolution stabilizes, workspace isolation increases) — there is no case where a user would prefer a workspace *without* git. Making it opt-in would mean users who forget the flag continue to get the broken downstream behavior described in Context.

**2. Separate `kodehold git init` command only (no auto-init).**
Rejected: Auto-init ensures that every new workspace starts with git presence from the moment of creation. A separate command would require users to discover and remember it. Auto-init is also cheap (a single `git init` + empty commit) and guarded with graceful degradation.

**3. Prompt user interactively ("Initialize git? [Y/n]").**
Rejected: KodeHold commands are designed to work in non-interactive scripts and CI pipelines. Interactive prompts would break automated workflows. Graceful degradation (warn, never fail) is the preferred non-interactive approach.

**4. Use `git clone --template` or other templating mechanism.**
Rejected: Over-engineering for the problem. A simple `git init` followed by `git add -A && git commit` is idiomatic, well-understood, and easy to audit. Templates would add complexity without meaningful benefit.

### Testing Strategy

| Test | Scenario | Expected Outcome |
|------|----------|------------------|
| `ws_init` with git available | Run `ws_init test-ws` | `[ -d "$ws_dir/.git" ]` exists, `git -C "$ws_dir" log --oneline` shows one commit |
| `ws_adopt` on non-git directory | Run `ws_adopt /tmp/non-git-project` | Git repo created with initial commit |
| `ws_adopt` on existing git repo | Run `ws_adopt /tmp/existing-git-project` | No re-init; guard clause skips; existing history preserved |
| `ensure-git` on missing workspace | Run `ensure-git nonexistent` | Fails with "Workspace not found" error |
| `ensure-git` on existing git workspace | Run `ensure-git` on a git-backed workspace | Passes with "already has a git repository" |
| Git unavailable | Temporarily hide git from PATH, run `ws_init` | Warning emitted, workspace created without `.git` |
| `git init` fails (read-only FS) | Run on a non-writable directory | Warning emitted, no abort |

## Consequences

### Positive

1. **Commit protection protocol works reliably.** `scripts/gate.sh` checks at lines 250 and 312 now operate on a guaranteed `.git` directory. The REVIEW gate correctly enforces review message requirements and working tree cleanliness.

2. **Slug resolution is deterministic.** `basename(git rev-parse --show-toplevel)` (ADR-0036 priority 2) always succeeds for git-backed workspaces, producing a consistent slug regardless of `cwd`. This eliminates the silent fallthrough to `basename(cwd)` and the potential slug mismatch between catalog entries and agentmemory hooks.

3. **Workspace isolation.** Each workspace has its own git repo, completely independent of the parent KodeHold repo. `git diff`, `git log`, and `git status` within a workspace directory reflect only that workspace's state — not the parent repo's.

4. **Zero-touch for users.** New workspace creation (`init`) and adoption (`adopt`) automatically include git setup. Users do not need to remember an extra step or flag.

5. **Backwards compatible.** Existing workspaces with `.git` are untouched. The `ensure-git` subcommand is opt-in for backfilling. No changes to catalog format, gate logic, or state files.

6. **Clean separation of concerns.** For adopted projects, the initial commit captures original source without KodeHold artifacts. This makes `git diff` between "pre-KodeHold" and "post-KodeHold" states meaningful.

7. **Traceability.** The distinct commit messages (`"Initial commit"`, `"Initial commit — adopted by KodeHold"`, `"Initial commit — backfilled by KodeHold"`) make it easy to identify how a workspace's git repo was created.

### Negative

1. **Warnings on systems without git.** Environments that lack `git` (minimal CI containers, restricted sandboxes) will see a warning on every `init` or `adopt` call. The operation succeeds, but the warning may cause confusion or noise in automated output.

2. **Auto-generated initial commits are not meaningful.** The initial commit message is generic — it does not describe the actual content of the workspace. For adopted projects this is partially mitigated by the pre-artifact timing (the commit captures original source code), but the message itself is still generic.

3. **Delicate timing dependency.** The insertion point in `ws_adopt()` matters: git init must happen *after* the commit count check (which reads from the existing repo) but *before* design doc creation (which should not be tracked). If code is reorganized in the future, this ordering could be accidentally violated.

4. **Existing non-git workspaces are not automatically fixed.** The `ensure-git` subcommand requires explicit invocation per workspace. Users may not realize they need to run it. Mitigation: the `ws_list` command could be updated to flag workspaces without `.git`.

### Neutral

1. **Initial commit in empty workspaces.** For `ws_init()`, the initial commit contains only `.gitignore` (all other files are templates that aren't meaningful as tracked source). This is harmless — the commit serves as a git baseline, not as meaningful history.

2. **Adopted project `.gitignore` is left unchanged.** The decision does not modify or create `.gitignore` in adopted projects. KodeHold artifacts remain untracked organically (they are created after the initial commit). If a user wants to explicitly ignore them, they must add entries to their own `.gitignore`.
