## Context

### The Problem

KodeHold has a rich ADR system — 39 ADRs at time of writing, many with multi-phase implementation plans. Examples include:

- **ADR-0035** (Custom KodeHold Viewer): 6 phases (Phase 1–6), with an explicit Phase tracking system in the ADR header
- **ADR-0040** (Headroom Integration): 4 phases (Phase 1: `headroom learn`, Phase 2: MCP Tools, Phase 3: Evaluation, Phase 4: Proxy)
- **ADR-0031** (Actions + Crystals): Multiple phases for rollout

Despite this, there is no single visual overview that tracks:

1. **Which phase** each ADR is currently in
2. **How many phases** each ADR has total
3. **Which phase status** (done / in-progress / not-started) each phase has
4. **What is complete vs. still pending** across all ADRs

A user who returns after a week has no quick way to answer "what ADR phases are still in-flight?" They must open each ADR file individually and scan the header.

### Current State

| Aspect | Current | Desired |
|--------|---------|---------|
| ADR phase tracking | Ad-hoc, inconsistent format in headers | Structured YAML frontmatter |
| Visual overview | None — must open each ADR | Board view in the custom viewer |
| Auto-generated index | No JSON index | `adr-index.json` generated by a sync script |
| Git-tracked phase info | No — phase is in prose headers | Yes — in YAML frontmatter |
| Agentmemory integration | None | Phase status updates stored as memories |

### Prior Art

| Approach | Description | Status |
|----------|-------------|--------|
| ADR-0035 (Custom Viewer) | Single HTML viewer at `tools/viewer/index.html` with tab system | Accepted — base platform for this ADR |
| ADR headers with Phase fields | ADR-0035 v2.0, ADR-0040 use ad-hoc `**Phase:**` lines in headers | Inconsistent — no machine-readable format |
| `tools/viewer/adr-index.json` | (Does not exist yet) | Planned |
| ADR README tables | `docs/adr/README.md` lists all ADRs with status, no phase info | Current — insufficient for phase tracking |

### Key Forces

1. **Git-tracked, not database-bound.** Phase info must live in the ADR files themselves (YAML frontmatter), not only in agentmemory. Git history preserves phase transitions.

2. **Backwards-compatible.** Existing ADRs without phase info must render correctly — as single-phase, completed entries.

3. **Zero new infrastructure.** The viewer already exists (ADR-0035). The JSON index is a static file served alongside the viewer. No new servers, databases, or services.

4. **Opt-in for ADR authors.** Phase blocks are optional. An ADR without a phase block is treated as a completed single-phase ADR. No need to retroactively add phase info to every existing ADR.

5. **Sync-script, not manual updates.** Generating `adr-index.json` must be automated — a script parses all ADR files, extracts frontmatter, and writes the index.

### Alternatives Considered

| Alternative | Pros | Cons | Verdict |
|------------|------|------|---------|
| **Separate JSON data store** (f.eks. `docs/adr/phases.json`) | Ren separation, ingen YAML i ADR'er | Drift — to filer skal holdes synkroniseret; ingen git-history på fase-info i ADR commit | ❌ Afvist — for høj risiko for drift |
| **Agentmemory-only storage** | Viewer kan query'e direkte | Ikke git-tracked; ingen synlighed i PRs; tabes hvis agentmemory reset'es | ❌ Afvist — kun supplement |
| **Tags on agentmemory actions** | Zero new infra | Konflikt mellem action-tracking og ADR-faser; bryder separation of concerns | ❌ Afvist |
| ✅ **YAML frontmatter in ADRs** (valgt) | Git-tracked, co-located, human-editable, PR-synlig | Gør ADR-filer lidt mere komplekse | ✅ **Valgt** |

## Decision

### Datamodel: YAML Frontmatter Phase Block

ADR files gain an optional `phase` block in their YAML frontmatter:

```yaml
---
phase:
  current: 1
  total: 3
  names:
    1: "Tab in viewer (MVP)"
    2: "Move-to dropdown interaction"
    3: "Standalone drag-and-drop board"
  status:
    1: done
    2: in-progress
    3: not-started
---
```

Fields:

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `phase.current` | integer | Yes (if `phase` exists) | Current active phase number (1-indexed). Must be `>= 1` and `<= total`. |
| `phase.total` | integer | Yes (if `phase` exists) | Total number of phases. Must be `>= 1`. |
| `phase.names` | object | No | Human-readable names for each phase number. Keys are integers (1-indexed). |
| `phase.status` | object | Yes (if `phase` exists) | Status for each phase. Keys are integers. Values: `done`, `in-progress`, `not-started`. |

**Default (no phase block):** Existing ADRs without `phase` frontmatter are treated as:

```yaml
phase:
  current: 0
  total: 1
  status:
    1: done
```

This ensures backwards compatibility — every ADR appears in the board.

**Status values:**

| Value | Meaning | Visual |
|-------|---------|--------|
| `done` | Phase implementation is complete | Green |
| `in-progress` | Phase is actively being worked on | Yellow/amber |
| `not-started` | Phase has not been started yet | Gray |

### Sync Script: `scripts/sync-adr-index.sh`

A bash script that reads all `docs/adr/ADR-*.md` files, parses their YAML frontmatter, and generates `tools/viewer/adr-index.json`.

**Input:** `docs/adr/ADR-*.md` files
**Output:** `tools/viewer/adr-index.json`
**Trigger:** Run by Scribes after ADR creation or update

**Output format:**

```json
{
  "updatedAt": "2026-06-05T12:00:00Z",
  "adrs": [
    {
      "id": "ADR-0035",
      "title": "Custom KodeHold Viewer",
      "status": "Accepted",
      "phase": {
        "current": 1,
        "total": 3,
        "names": {
          "1": "Tab in viewer (MVP)",
          "2": "Move-to dropdown interaction",
          "3": "Standalone drag-and-drop board"
        },
        "status": {
          "1": "done",
          "2": "in-progress",
          "3": "not-started"
        }
      }
    },
    {
      "id": "ADR-0001",
      "title": "KodeHold Foundation and Principles",
      "status": "Accepted",
      "phase": {
        "current": 0,
        "total": 1,
        "status": { "1": "done" }
      }
    }
  ]
}
```

**Implementation approach (bash + yq):**

```bash
#!/usr/bin/env bash
# sync-adr-index.sh — generate tools/viewer/adr-index.json from ADR YAML frontmatter
set -euo pipefail

OUTPUT="tools/viewer/adr-index.json"
mkdir -p "$(dirname "$OUTPUT")"

# Start JSON
echo '{' > "$OUTPUT"
echo '  "updatedAt": "'$(date -u +%Y-%m-%dT%H:%M:%SZ)'",' >> "$OUTPUT"
echo '  "adrs": [' >> "$OUTPUT"

FIRST=true
for f in docs/adr/ADR-*.md; do
  # Skip backup files created by memory_compress_file
  [[ "$(basename "$f")" == *.original.md ]] && continue
  $FIRST || echo ',' >> "$OUTPUT"
  FIRST=false

  id=$(basename "$f" | sed 's/\.md$//' | sed 's/^\(ADR-[0-9]\{4\}\).*/\1/')
  title=$(sed -n 's/^# //p' "$f" | head -1)
  status=$(sed -n '/^## Status/,/^## /p' "$f" | grep -E '^(Proposed|Accepted|Deprecated|Superseded)$' | head -1)

  # Parse YAML frontmatter for phase block via yq
  phase_json=$(sed -n '/^---$/,/^---$/p' "$f" | sed '1d;$d' | yq eval '.phase' - 2>/dev/null || echo "null")

  if [ "$phase_json" = "null" ] || [ -z "$phase_json" ]; then
    phase_json='{"current":0,"total":1,"status":{"1":"done"}}'
  fi

  cat >> "$OUTPUT" <<ENTRY
    {
      "id": "$id",
      "title": $(echo "$title" | jq -R -s '.'),
      "status": "$status",
      "phase": $phase_json
    }
ENTRY
done

echo '  ]' >> "$OUTPUT"
echo '}' >> "$OUTPUT"

echo "Written: $OUTPUT ($(jq '.adrs | length' "$OUTPUT") ADRs)"
```

**Alternative:** Python implementation if `yq` is not available — using standard library `yaml` and `json` modules:

```python
#!/usr/bin/env python3
import json, re, sys, yaml
from datetime import datetime, timezone
from pathlib import Path

ADRS_DIR = Path("docs/adr")
OUTPUT = Path("tools/viewer/adr-index.json")

adrs = []
for f in sorted(ADRS_DIR.glob("ADR-*.md")):
    if f.name.endswith('.original.md'):
        continue
    text = f.read_text()
    m = re.match(r'^---\n(.*?)\n---', text, re.DOTALL)
    if m:
        try:
            frontmatter = yaml.safe_load(m.group(1))
        except yaml.YAMLError:
            frontmatter = {}
    else:
        frontmatter = {}

    id_match = re.match(r'(ADR-\d{4})', f.stem)
    title_match = re.search(r'^# (.+)$', text, re.MULTILINE)
    status_match = re.search(r'^(Proposed|Accepted|Deprecated|Superseded)$', text, re.MULTILINE)

    phase = frontmatter.get("phase")
    if not phase:
        phase = {"current": 0, "total": 1, "status": {"1": "done"}}

    adrs.append({
        "id": id_match.group(1) if id_match else f.stem,
        "title": title_match.group(1) if title_match else f.stem,
        "status": status_match.group(1) if status_match else "Proposed",
        "phase": phase
    })

output = {"updatedAt": datetime.now(timezone.utc).strftime("%Y-%m-%dT%H:%M:%SZ"), "adrs": adrs}
OUTPUT.parent.mkdir(parents=True, exist_ok=True)
OUTPUT.write_text(json.dumps(output, indent=2))
print(f"Written: {OUTPUT} ({len(adrs)} ADRs)")
```

### Board Layout: 5 Columns

The ADR Phases tab in the viewer renders a kanban-style board with 5 columns:

| Column | Shows ADRs where... | Visual |
|--------|-------------------|--------|
| **Proposed** | `status: Proposed` (no phase started) | Gray header |
| **Phase 1** | `phase.current == 1` | Blue header |
| **Phase 2** | `phase.current == 2` | Blue header |
| **Phase 3** | `phase.current == 3` (or higher if total > 3) | Blue header |
| **Complete** | `phase.current >= phase.total` or Accepted with no phase block | Green header |

**Column rendering rules:**

1. **Proposed column** — ADRs with `status: Proposed` AND no phase block. These are purely conceptual — no implementation has begun.
2. **Phase N columns** — ADRs where `phase.current == N`. If an ADR has more than 3 total phases but is currently in Phase 1, it appears in Phase 1. The board shows up to 3 active phase columns; ADRs with `phase.current >= 4` could be handled by an ellipsis column or by extending the board in Phase 2.
3. **Complete column** — All ADRs where implementation is done: `phase.current >= phase.total` and `phase.status[total] == done`. Also includes all legacy ADRs (no phase block, Accepted) — they are implicitly complete.

**Card design (each ADR):**

```
┌──────────────────────────────┐
│ ADR-0035        ●●●○         │
│ Custom KodeHold Viewer       │
│ [Accepted]   Phase 1 of 3   │
│ Phases: ■□ □                  │
│ Last changed: 2026-06-02    │
└──────────────────────────────┘
```

- **Progress dots:** Filled for done phases, half-filled for current, empty for not-started
- **Phase bar:** `■` = done, `▣` = in-progress, `□` = not-started
- **Status badge:** Same styling as existing viewer badges
- **Last changed:** From git log or agentmemory (see Agentmemory supplement)

### Viewer Integration

**Tab:** New "ADR Phases" tab in `tools/viewer/index.html`.

**Data source:** Primary: `./adr-index.json` (co-located in `tools/viewer/`). The viewer fetches it via a relative URL:

```javascript
const response = await fetch('./adr-index.json');
const data = await response.json();
```

> **Note:** Although phase info is primarily stored in ADR YAML frontmatter, the sync script generates `adr-index.json` som et maskinlæsbart JSON data store. Dette JSON-dokument kan queries af andre værktøjer (CI dashboards, rapporter, scripts) uden at parse YAML eller Markdown.

**Agentmemory supplement:** For "last changed" timestamps on each ADR card, the viewer may query agentmemory for recent memories mentioning the ADR number. This is a Phase 2 enhancement.

**Read-only Phase 1 (MVP):**
- Fetches `adr-index.json` on tab activation
- Renders the 5-column kanban board
- Each card is clickable — opens the ADR file via a relative link to `docs/adr/<filename>.md`
- No write operations — the board is a pure visualization

**Phase 2 (future):**
- "Move to next phase" button on each card
- Agentmemory sync — writing phase transitions
- Interactive phase bar editing

#### Phase 2 — Agentmemory Integration

Når en ADR fase skrider frem (f.eks. via "Move to next phase" knap), lagres overgangen i agentmemory:
- `memory_save(content="ADR-0035 phase 2 → in-progress", type="fact", concepts="adr-phase, adr-0035", project="kodehold")`
- Board'et kan query'e `GET /agentmemory/memories?concepts=adr-phase` for "last changed" timestamps
- Director kan bruge agentmemory phase-data til at prioritere actions: hvis en ADR er i Phase 2, skal actions med `requires` dependency på den ADR aktiveres

This makes the board more than a status display — it becomes an action-priority driver in future versions.

**Phase 3 (future):**
- Standalone drag-and-drop board
- Drag cards between columns to advance phases
- Auto-commits to ADR frontmatter and regenerates `adr-index.json`

## Consequences

### Positive

1. **Instant visual overview.** One tab shows all 39+ ADRs organized by implementation phase — Proposed, Phase 1-3, Complete. No need to open each file.

2. **Git-tracked phase info.** Phase metadata lives in YAML frontmatter in the ADR files, versioned in git. Phase transitions are visible in commit history.

3. **No new infrastructure.** The viewer already exists (ADR-0035). The JSON index is a static file. No new databases, servers, or background processes.

4. **Backwards compatible.** ADRs without phase frontmatter are treated as implicitly complete. No need to retroactively update all 39 existing ADRs.

5. **Machine-readable index.** `adr-index.json` can be consumed by other tools — CI dashboards, token reports, team meeting agendas.

6. **Zero token cost.** The board runs entirely in the browser — no LLM inference required.

7. **Sync script is self-contained.** `scripts/sync-adr-index.sh` depends only on `yq` and `jq` (or Python stdlib) — both common in development environments.

8. **Phased rollout.** The MVP (Phase 1) is read-only and immediately useful. Phase 2 and 3 add interactivity incrementally.

### Negative

1. **YAML frontmatter adds complexity.** ADR files now have a `---` delimited block before the Markdown content. Some editors may not render YAML frontmatter gracefully.

2. **Sync script is a new maintenance burden.** If the ADR filename format or frontmatter schema changes, the script must be updated. Scribes must remember to run it after every ADR change.

3. **`adr-index.json` can become stale.** If the sync script is not run after creating or updating an ADR, the index will be out of date. Mitigation: run the script as a git hook or CI step.

4. **Existing ADRs lack phase info.** 39 ADRs need to be read and understood to assign accurate phase info. While the board works without it (treating them as "complete"), the board is most useful when ADRs with active implementation phases have phase blocks.

5. **Viewer tab must handle 404 gracefully.** If `adr-index.json` does not exist, the tab should show a clear setup message rather than an error.

### Risks

| # | Risk | Likelihood | Impact | Mitigation |
|---|------|-----------|--------|------------|
| 1 | **Sync script not run after ADR update** | Medium | Medium | Add `sync-adr-index.sh` call to ADR creation workflow in scribes.md. Consider git pre-commit hook. |
| 2 | **YAML frontmatter breaks existing ADR parsing** | Low | High | The script uses `sed` to extract frontmatter between `---` markers — ADRs without frontmatter are handled by the default case. Existing ADRs without `---` are unaffected. |
| 3 | **`yq` not available on all systems** | Low | Low | Fall back to Python implementation. Both alternatives are documented in the ADR. |
| 4 | **ADR file paths change** | Low | Medium | The script globs `docs/adr/ADR-*.md` — if the directory structure changes, the glob must be updated. |
| 5 | **Viewer tab performance with 50+ ADRs** | Low | Low | The board renders a fixed set of cards (<100). No pagination needed. |
