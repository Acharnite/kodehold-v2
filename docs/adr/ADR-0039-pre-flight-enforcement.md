# ADR-0039: Pre-Flight Knowledge Check Enforcement

## Status

Accepted

**Note (ADR-0050):** The pre-flight knowledge recall using `agentmemory_memory_recall` has been replaced by OpenCode's `search_semantic` tool. See ADR-0050 for details.

**Version:** 1.1
**Last Updated:** 2026-06-03

## Context

### The Problem

The Director has a **Pre-Task Knowledge Flow** protocol defined in `director.md` (§Pre-Task Knowledge Flow, lines 37-56). Before every delegation, the Director MUST run three recall steps:

1. `memory_lesson_recall` — recall relevant lessons
2. `memory_patterns` — detect patterns
3. `memory_recall` — check recent decisions

However, this protocol is **routinely skipped**. The section exists as a separate block in the Director's prompt — a "nice to have" rather than a hard dependency of the delegation flow. The Director frequently delegates work without any knowledge recall, resulting in:

- **Repeated mistakes.** The Director spent an hour debugging agentmemory patches when a 2-second `memory_lesson_recall` would have surfaced the relevant lesson immediately.
- **Wasted team effort.** Teams receive tasks without context of prior learnings, leading to redundant investigation and rework.
- **Protocol erosion.** When a mandatory protocol is routinely skipped, it signals that all protocols are optional — undermining the entire KodeHold discipline model.

### Existing Infrastructure

The knowledge flow infrastructure already exists:

| Component | Location | Purpose |
|-----------|----------|---------|
| Pre-Task Knowledge Flow section | `director.md` lines 37-56 | Defines the 3-step recall protocol |
| Agentmemory Knowledge Flow skill | `.opencode/skills/agentmemory-knowledge-flow/SKILL.md` | Pre-task recall for subagents |
| ADR-0030 | `docs/adr/ADR-0030-agentmemory-knowledge-flow.md` | Defines the knowledge flow protocol |
| ADR-0038 | `docs/adr/ADR-0038-knowledge-recall.md` | Fixes recall path (project scope, team tags, limits) |
| Action Frontier Protocol | `director.md` §Action Frontier Protocol | The delegation flow that pre-flight checks should gate |

The recall path is now **working** (fixed by ADR-0038). The problem is not the recall mechanism — it's the **enforcement** of the recall step.

### Key Forces

1. **100% compliance required.** The protocol must be impossible to skip accidentally. If the Director can delegate without running recall, the protocol will be bypassed.
2. **Low overhead.** Adding 2-3 agentmemory API calls before each delegation is acceptable (~1-2 seconds). Anything that adds significant latency (calls to external APIs, running scripts) will be skipped in practice.
3. **Simple to implement.** The fix should be a targeted change to `director.md`, not a new infrastructure component or framework modification.
4. **Self-documenting.** The enforcement mechanism must be visible in the delegation flow itself — not hidden in a separate section that the model can ignore.
5. **Model-agnostic.** The enforcement must work regardless of which LLM powers the Director. Prompt-level protocols fail on smaller models that skip steps.

## Decision

### Recommended: Option 1 (Enforce in Action Frontier Protocol) with Option 3 (Context Injection) as Complement

We implement a **two-part enforcement** strategy:

#### Part A: Bake Pre-Flight into the Delegation Flow (Option 1)

The Action Frontier Protocol's Delegation Flow (currently 7 steps) gets a new step inserted:

```
1. memory_action_create
2. memory_frontier
3. memory_lease
4a. PRE-FLIGHT KNOWLEDGE RECALL ← NEW MANDATORY STEP
4b. Task tool delegation (includes recall output in prompt)
5. memory_action_update
6. memory_crystallize
7. memory_lease release
```

Step 4a replaces the standalone "Pre-Task Knowledge Flow" section. The recall is now a numbered step in the delegation sequence — not a separate section that can be skipped.

The existing 3-step recall is preserved but **restructured** into a single streamlined call:

```
agentmemory_memory_lesson_recall(query="<delegation-topic> <team>", limit=5, project="<project>")
agentmemory_memory_recall(query="<delegation-topic>", limit=3)
```

The `memory_patterns` step is removed — it duplicates what `memory_lesson_recall` already provides (ADRs generated by crystals already feed into lessons via the consolidation pipeline). This keeps overhead minimal.

The recall **output** is captured and stored as a local variable — not just run and forgotten. This enables Part B.

#### Part B: Inject Recall Results into Every Task Prompt (Option 3 Complement)

The recall output from Part A becomes **a mandatory input to the Task tool prompt**. Every delegation prompt MUST include a `Relevant Context` section populated with the recall results:

```
Task tool:
  subagent_type: <team>
  prompt: |
    Context:
    - Design doc section: <ref>
    - Relevant files: <paths>
    - Relevant Context from agentmemory:
      Lessons: <recall results from step 4a>
      Recent decisions: <recall results from step 4a>
    - Current state: <done so far>
    Task: <specific task>
    Deliverables: <what to return>
```

This achieves **structural enforcement**: if the Director skips the pre-flight recall, the Task prompt will be visibly missing its `Relevant Context` section. The missing section is obvious to both the Director (when writing the prompt) and the subagent (when receiving it), creating a self-correcting feedback loop.

**Why this combination succeeds where each alone would fail:**

| | Option 1 alone | Option 3 alone | Both combined |
|---|---|---|---|
| Compliance | Medium — prompt-level | Medium — relies on injection mechanism | **High** — structural + visible |
| Overhead | Low | Low | Low |
| Implementability | Easy — doc change | Medium — needs mechanism | **Easy** — doc change only |
| Self-documenting | High — in flow | Medium | **High** — both flow and prompt |

#### Part C: Remove Standalone Pre-Task Knowledge Flow Section

The existing "## Pre-Task Knowledge Flow" section (director.md lines 37-56) is removed and its content is absorbed into the renumbered Delegation Flow. This eliminates the "separate section that can be skipped" problem at the root.

### Summary of Changes to `director.md`

| Change | Location | Description |
|--------|----------|-------------|
| **Remove** | §Pre-Task Knowledge Flow (lines 37-56) | Replaced by inline step in Delegation Flow |
| **Rename** | §Action Frontier Protocol → §Delegation Flow | More precise section title |
| **Insert step 4a** | §Delegation Flow, between lease and Task | New mandatory pre-flight recall step |
| **Update step 4b** | §Delegation Flow | Task prompt now requires `Relevant Context` section |
| **Append** | §Delegation Flow | Note: "If the Task tool prompt lacks a `Relevant Context` section, the pre-flight recall was skipped — STOP and re-run step 4a." |

### Rationale

**Why not Option 2 (Sentinel) as primary?**
Sentinels are passive — they can detect a violation but cannot block the delegation. The Director would receive a warning after the fact, at which point the damage is done (wasted subagent invocation, wasted tokens). Sentinels also require a watcher process or periodic polling, adding infrastructure complexity for weaker enforcement.

**Why not Option 3 (Skill auto-load) alone?**
True skill auto-load on Task tool would require changes to OpenCode's subagent invocation mechanism — a framework-level change outside KodeHold's control. The simplified version (inject recall results manually) achieves the same effect without framework changes.

**Why `memory_patterns` is removed:**
`memory_patterns` detects cross-session patterns and overlaps with the lessons returned by `memory_lesson_recall`. Since ADR-0038 (and the `kodehold-learnings` companion lessons) make lessons discoverable by team and topic, `memory_patterns` adds overhead without unique value. Crystals (ADR-0033) already feed pattern-detected insights into lessons via the consolidation pipeline.

## Consequences

### Positive

1. **Near-100% compliance.** The pre-flight recall is a numbered step in the delegation flow, and its output is structurally required by the Task prompt format. Skipping it produces an obviously incomplete prompt.

2. **No infrastructure changes.** Everything is implemented via documentation changes to `director.md`. No new MCP tools, no agentmemory schema changes, no sentinel infrastructure.

3. **Lower overhead than current protocol.** The current Pre-Task Knowledge Flow has 3 steps (lesson recall + patterns + memory recall). The new flow reduces this to 2 steps by removing `memory_patterns`. Total overhead: ~2 agentmemory API calls (~1 second).

4. **Self-documenting enforcement.** The `Relevant Context` section in every Task prompt makes the pre-flight visible to both the Director and the subagent. A missing section is a clear signal that the recall was skipped.

5. **Eliminates duplicate protocol.** The standalone "Pre-Task Knowledge Flow" section was redundant with what should have been part of the delegation flow. Removing it reduces prompt surface area and eliminates the "skip-able section" failure mode.

6. **Better subagent context.** Subagents receive relevant lessons and decisions as part of their prompt, improving their first-attempt quality without needing to run their own knowledge flow.

### Negative

1. **Token overhead per delegation.** Each delegation prompt is larger by the recall results (typically 200-500 tokens). This is negligible compared to typical delegation prompts (2K-8K tokens).

2. **Prompt-level enforcement ceiling.** The Director can still skip the pre-flight step if the model chooses to ignore the flow diagram. However, the visible `Relevant Context` section requirement raises the cost of skipping — it's no longer a silent omission.

3. **`memory_patterns` removed.** Teams relying on `memory_patterns` for cross-session pattern detection lose that specific signal. Mitigation: crystals (ADR-0033) already feed into lessons, so pattern-detection happens through the consolidation pipeline rather than the direct `memory_patterns` call.

### Risks

| # | Risk | Likelihood | Impact | Mitigation |
|---|------|-----------|--------|------------|
| 1 | **Director model ignores the renumbered flow** | Medium | High | This is the same risk as the current protocol. Mitigation: the `Relevant Context` section requirement makes omission obvious. |
| 2 | **Recall results too long for Task prompt** | Low | Low | Keep `limit=5` for lessons and `limit=3` for decisions. If results are verbose, summarize. |
| 3 | **Teams rely on `memory_patterns`** | Low | Low | Pattern detection still happens through consolidation. If a team explicitly requests pattern data, a targeted call can be made. |

### Post-Review Additions (Second Opinion)

The following refinements were added after review and second opinion approval:

1. **Error handling for recall failures.** If `memory_lesson_recall` or `memory_recall` fails due to timeout or error, log a warning, skip the pre-flight step, and continue with delegation. Recall failure must never block work.

2. **Context length guard.** If recall results exceed ~800 characters, truncate the `Relevant Context` section to prevent token waste. This keeps delegation prompts lean.

3. **Hotfix exemption for P0 emergencies.** For priority-zero or emergency situations, the Director may skip pre-flight with explicit user approval and a logged reason. The exemption must be visible in the delegation record.

These additions preserve the ADR's core enforcement mechanism while adding pragmatic safeguards against edge cases.

## Alternatives Considered

### Option 1: Enforce in Action Frontier Protocol (Selected — Primary)

Bake pre-flight into the delegation flow itself as a numbered step between `memory_lease` and `Task tool`. This ADR's recommended approach when combined with Option 3's context injection.

**Why it works as primary:** It's the simplest change with the highest impact. The delegation flow is the Director's single most-followed prompt section — everything that is a numbered step gets executed.

**What it needs to be 100%:** Requires the context injection (Part B) to provide structural enforcement. Without Part B, it's still prompt-level.

### Option 2: Sentinel/Watch (Rejected)

Use agentmemory's sentinel system to watch for delegation patterns and trigger a pre-flight reminder. A sentinel would detect when the Director starts a delegation without having recently checked lessons.

**Positive:**
- Technical enforcement rather than prompt-level
- Decoupled from Director implementation

**Negative:**
- Sentinels are passive — they can warn but cannot block
- Complex to implement: needs a watcher process or polling loop, state tracking, and a correlation mechanism to detect "delegation without prior recall"
- Not self-documenting — the enforcement is invisible to anyone reading the protocol
- Does not achieve 100% compliance (Director receives warning after delegation starts)

**Why rejected:** The weakest compliance for the highest implementation cost. Sentinel infrastructure would need to be built (no existing "watch delegation" sentinel exists), and even then it only provides post-hoc warnings.

### Option 3: Skill Auto-Load (Rejected — Adopted as Complementary Technique)

Make the `agentmemory-knowledge-flow` skill auto-load before EVERY delegation. When the Director uses `Task tool`, the skill is injected automatically with the delegation topic.

**Positive:**
- Transparent to the Director (no behavior change needed)
- Subagent always has context

**Negative:**
- True auto-injection requires framework-level changes (OpenCode's subagent invocation mechanism)
- Would need either: a plugin that intercepts Task tool calls, or a modified skill loader
- Even if auto-loaded, the skill only provides the protocol — the subagent still needs to execute it
- The Director is the one who should run pre-flight, not the subagent (wrong layer)

**Why rejected as primary:** Too complex for what it achieves, and solves the wrong problem (subagent context vs. Director discipline). However, the principle of injecting recall results into the Task prompt is sound — this ADR adopts it as the context injection mechanism in Part B.

### Do Nothing (Rejected)

Leave the Pre-Task Knowledge Flow as a standalone section that the Director can skip.

**Why rejected:** The entire motivation for this ADR is that the current approach demonstrably fails. The Director (a human or AI orchestrator) routinely skips the pre-flight check, wasting team effort. Continued inaction allows the protocol to erode further.

## Open Questions

1. **Should `memory_patterns` be restored if teams report losing signal?** Yes — we can re-add it as an optional step (only run if delegation topic matches pattern-detectable domains like "bug trends" or "recurring issues"). Decision deferred until feedback arrives.

2. **What about workspace projects (e.g., `bob`)?** The same pre-flight pattern applies — project-scoped recall should use the workspace's slug. The flow in `director.md` is project-agnostic.

3. **Should subagents also receive the pre-flight results?** Yes — that's the entire point of Part B's context injection. The subagent gets relevant lessons directly, reducing the need for the subagent to run its own pre-task knowledge flow for domain context.
